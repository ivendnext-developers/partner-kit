# The Wasm extension-point contract — what a sandboxed function promises, per extension point (kit v2)

**For:** a developer writing a sandboxed function (a WebAssembly module) for one of iVendNext's published extension points. **One text** with the host contract the first spike proved ([`HOST_CONTRACT.md`](HOST_CONTRACT.md), cited by section, never restated), plus what the kit adds. Where this file and an extension point's spec disagree, the spec wins and this file is the defect. A `P-` name (P-WASM, P-CHECK, …) is the handle of that spec; guide chapter 9 lists the same extension points by plain names instead, given beside each handle in §3 — P-WASM, the host itself, is chapter 9's *A host for sandboxed functions*.

## 1. The host contract (unchanged from the spike)
- **Input and output:** canonical UTF-8 JSON; money in integer minor units, quantity in integer thousandths (`qty_milli`); no float, no sign, no exponent; nesting at most 32 — `HOST_CONTRACT.md` §2.
- **Validation:** check fields in the published order and answer `{"error":"invalid_input","at":"<first failing path>"}` — §3.
- **Output escaping:** `\" \\ \b \f \n \r \t`, other control characters as `\u00xx` (lower-case), everything else raw — §4.
- **Host interface:** the native profile `pp` — `pp.read_input`, `pp.write_output`, `pp.log`, export `run() -> i32` and `memory` — and nothing else: a clock, randomness, the network or a start function are refused at load — §5.
- **Limits:** fuel 11 000 000 units; memory 160 pages (10 MiB, written into the module at publish); answer 512 KiB; log 1 KiB; a fresh instance per call; the 1 000 ms wall clock is a backstop only and **never decides an answer** (P-WASM §5).

## 2. What the kit adds
| Rule | Why | Where |
|---|---|---|
| **No floating-point instruction** in an extension point that touches a price or a decision; **no SIMD**; **no atomics, ever** | a float's result can differ by host (P-WASM §4). Measured: a common JSON library put 26 float instructions into the first spike's adjuster — the template carries its own integer-only JSON, 0 float instructions | `scan.py`, `kit.py static_checks` |
| **The stack bound:** each call adds its frame cost (parameters + locals + 4) to an in-module counter; past **10 000 units** the module traps `integer_overflow` | an engine's stack is its own size and moves with warm-up (measured: server 10 000, Chrome 8 000, Node 50 000+ levels), so a deep chain could answer on one host and trap on the other. The counter trips at the same call on every host **as long as it trips before an engine's own stack runs out** — measured for one deliberately recursive module. ⚠ The unit cost ignores operand-stack depth and spills: a function with a native frame far larger than its locals suggest is UNPROVEN. Keep recursion shallow. ⚠ A large local array per call ends the module's OWN memory stack first: with a 4 KB array per frame the call trapped `memory_out_of_bounds` at depth 253, below the counter, at the same depth on the server host, Node and Chrome (parity holds; the trap's reason depends on the shape). A 256-byte frame still trips the counter | `stackmeter/` (run at publish, before the fuel meter) |
| **Published through the kit's meters** (stack, then fuel) for any extension point that runs on the till | a till has no fuel counter of its own (measured) | `kit.py publish` |
| **At most 256 KB** after metering — for an extension point that runs on the **till**. A **server-only** extension point has **no size cap** | the till downloads and cold-starts the module; the server does neither on a cashier's clock | `kit.py SIZE_CAP`, `SERVER_ONLY_SIZE_CAP` |
| **Samples:** every extension point publishes its parity samples; `must_answer` marks the realistic ones a module must answer within its budgets; the others (stress) must give the identical result on both hosts, a fuel stop included | an oversized basket may legitimately exhaust the budget — but identically | `template/samples/samples.json` |
| **Server-only extension points** (they never run on a till — e.g. a P-RULES validate function, P-RULES §2 option B, which does decide: it refuses or passes a document) may use floats and SIMD and are run on the server host only, its own fuel the bound; a module carrying its own meter is refused on this path too | the float rule protects till/server agreement; with one host there is nothing to disagree with | `kit.py admit --server-only` |

## 3. The extension points that take a sandboxed function
| Extension point | Call | Runs | What the module receives and answers | Status |
|---|---|---|---|---|
| **P-PRICE** (*Pricing condition-and-adjuster*) | `price/1` | server **and** till (offline) | the cart's lines, each with the promotion already taken (`promotion_discount_minor`), and the condition's configuration → per-line discounts taken after the promotions ([contract page](../../contracts/pages/price.md), [schema](../../contracts/extension_contracts/price.v1.schema.json)). **The template's worked example is this module** (a member discount; the POS app's own test module) | built in the POS app (train T6) and pinned to CitiXsys's module certificate key: it runs a module we have certified once the retailer's administrator adds it in Desk, and a retailer's limit (`max_discount_percent`) is 0 until iVendNext raises it |
| **P-CHECK** (*Check before tender*) | `check/1` | server and till | the sale's context → `allow` · `refuse` · `ask` with a message | its module leg built in the POS app (train T6) and pinned to the certificate key: it runs a module we have certified once the retailer's administrator adds it in Desk |
| **P-CAPTURE** (*Capture on an event*) | `capture/1` | server and till (on scan) | the scanned line's context → `confirm` · `refuse` | spec; `wasm` leg follows P-WASM |
| **P-RULES** (*Save rules*; this leg later) | validate | **server only** | a document (serialised) → `ok` or a refusal | option (B), later |
Two extension points run a sandboxed function on a retailer's iVendNext today, P-PRICE and P-CHECK's module leg, and each runs only a module CitiXsys has certified, once the retailer's administrator adds it in Desk (the module certificate key is pinned in the POS app). The template's module is byte-identical to the POS app's own test module (`price_member.wasm`, sha256 `2950a196…`), which the POS app's tests run on its own hosts and which ran on our test bench's till screens, online and offline (2026-10-12); everything else proven here is proven on the kit's two hosts on a laptop.
